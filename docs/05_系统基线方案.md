## 0. 先把三件事说清楚

### 0.1 TreeOS 不是汉化包

对。汉化只是第 2 阶段的一小块。TreeOS 要交付的是：**一个自己能定基线、自己能发版的系统**。
汉化、主题、风扇、超频、预置启动文件、Flash 启动器，都是这个系统上的功能，不是全部。

### 0.2 "热更新"能改什么、不能改什么

`build/treeos-apply.sh` 这类脚本就是热更新，但它的**天花板是 glibc 2.30**。

| 能热更新 | 必须重新刷 / 换底座 |
|---|---|
| 开机画面、菜单汉化、主题、开机动画 | glibc 版本 |
| 风扇 PWM、超频档位（boot.ini 层面除外） | Mesa / 图形栈 |
| 预置 Flash 运行时、桌面入口、键位守护 | 内核 |
| 脚本、配置、service | 官方 Ruffle、Chromium |

**一句话**：热更新是"在旧地基上装修"，换底座是"重新打地基"。
装修可以天天做，打地基只能做一次（做完之后又回到可以热更新的状态）。

### 0.3 ArkOS4Clone 会不会变成 TreeOS

两条路，结果不同：

- **留在 A 路线（继续在 20261008 上打补丁）**：它是 **ArkOS4Clone 的一个衍生版**。
  只要上游还发新镜像，你就得每次把补丁重新打一遍。这不叫"自己的系统"，叫"跟版"。
- **走 B 路线（换底座）**：ArkOS4Clone 只剩 **菜单层 + 脚本层**（ES、`/opt/system`、
  `/usr/local/bin` 那一堆 bash）。系统本体换成 Debian。这时**才真的是 TreeOS**，
  ArkOS4Clone 退化成"从它那儿继承来的一段代码"，而不是"它就是 TreeOS"。

**分叉点就是换底座那一下。** 在那之前叫 remix，之后叫发行版。

> 许可证上两种都合法（MIT，保留版权声明 + `LICENSES/` 即可），差别是**工程归属**。

## A. 目标基线：Debian（13 优先，12 兜底）

| 候选 | glibc | 结论 |
|---|---|---|
| Ubuntu 19.10（现状） | 2.30 | ❌ 淘汰，已 EOL |
| Ubuntu 22.04 | 2.35 | 🟡 能用，但 2027-04 到寿，aarch64 生态杂 |
| **Debian 12 (bookworm)** | **2.36** | ✅ 稳妥选择，LTS 到 2028-06 |
| **Debian 13 (trixie)** | **2.41** | ✅ **首选**：当前 stable，LTS 到 2030 |
| Armbian | 跟随上游 | 🟡 板级支持好，但定制层厚，出问题难归因 |
| Buildroot（ROCKNIX 那类） | 自定 | ❌ 没有 apt，装官方 Ruffle/Chromium 就没意义了 |

**为什么首选 Debian 13**：这套系统的痛点就是"底座过寿"，所以要选**剩余寿命最长**的那个。
Debian 13 的 glibc 2.41 / Mesa 25 完全覆盖 Ruffle（要 2.32）和 Chromium（要 2.35），
且还能再吃 4 年安全更新。Debian 12 作为兜底（万一某个驱动在 13 上回归）。

**为什么不用 Ubuntu**：aarch64 上 Debian 更干净（无 snap、无 ubuntu-advantage 那套），
镜像小 1 GB 左右，对 1 GB 内存 + 小卡更友好。

**硬性前提（上机前必须确认）**：`/roms` 所在的 EASYROMS 分区大小和卡容量。
Debian + ES + 模拟器 + Ruffle + Chromium 的 rootfs 大约 **3.5–5 GB**，
比现在的 ArkOS rootfs 大。卡小于 32 GB 要做取舍（Chromium 可选装）。

## B. 内核：**必须升**，但可以分两步走

### B.1 为什么 4.4 留不住

不是 syscall 问题——glibc 2.41 的内核下限是 **3.2**，4.4 完全够，用户态能跑起来。
**卡住的是图形。** 现代 Mesa 的 `panfrost`（驱动 Mali-G31 的开源驱动）依赖
`drm/panfrost`，这个驱动 **5.10 才进主线**，4.4 里没有。所以在 4.4 上：

- Mesa 的 panfrost → 找不到设备，退回 llvmpipe 软件渲染（640×480 也许能跑，但 Chromium 没戏）
- 想用 GPU 只能走 **厂商 libmali 闭源 blob**（它配的是厂商内核驱动，跟 Mesa 无关）

### B.2 两条内核路线

| | **K1 · 保守** | **K2 · 正路** |
|---|---|---|
| 内核 | 保留 4.4.189 | 主线 **6.1 LTS**（Debian 自带）或 Rockchip 5.10 BSP |
| 用户态 | Debian 13 | Debian 13 |
| GL 来源 | 厂商 libmali（GLES，无 DRI3） | Mesa panfrost（EGL/GBM/**DRI3** 齐全） |
| Xorg | 大概率仍要 `AccelMethod none` | 可以正常加速 |
| Chromium | 基本没戏 | 有戏 |
| 工作量 | 小（1–3 天能出第一版） | 大（dts / 面板 / WiFi / 音频） |
| 风险 | 官方 Ruffle 能启动，但渲染可能仍黑 | 能不能点亮屏幕是唯一的大未知 |

**建议：K1 先出可刷的版本（把 glibc 天花板打掉，用户可以先用上官方 Ruffle 的壳），
K2 作为主线目标。** 两者共用同一套用户态，切换只换内核 + dtb。

### B.3 一个强线索（务必先验证）

掌机 `event3` 叫 **`odroidgo3-keys`** → 这台机器在设备树层面就是 **ODROID-GO Advance/Super 的同族**。
主线内核里已有 `rk3326-odroid-go3.dts`，ROCKNIX / 前 JELOS 这类项目就是靠它跑起来的。
**如果 RK3326+G31 有新 Mesa 的成功案例，那就是它**——但它们用的是 Buildroot，不带 apt。
我们的活是：把这套 **内核 + panfrost 的可行性**搬到一个 **Debian 用户态**上。

**R36S 的差异点**（山寨机改过屏/改过 WiFi）需要落到 dts 里：
面板时序（panel timings）、RTL8188EU、音频 codec 的时钟。这三处是 K2 的真实工作量来源。

### B.4 能不能"4.4 内核 + 新用户态"

能跑，但**拿不到 GL 加速**（见 B.1），等于把 01 的问题从"glibc 太老"换成"图形栈太老"。
所以这不是路线，只是一个中间态。

## C. 图形栈组合

**K2（目标形态）**

```
Mesa 25（Debian 13 自带）
  └─ panfrost  →  Mali-G31 (Bifrost)
       └─ drm/panfrost（内核 6.1+）
            └─ GBM → Xorg(modesetting, DRI3) / KMS/DRM 直出 / Wayland
```

| 项 | 选型 | 说明 |
|---|---|---|
| Mesa | 发行版自带（25.x） | 不要自己编，别再造一个"19.10 打补丁" |
| 后端 | **panfrost** | 开源、跟着 Mesa 走、DRI3/GBM 齐全 |
| 厂商 libmali | **只作兜底，不进默认路径** | 闭源、绑内核、跟 glibc 走不稳，是这次的老路 |
| Xorg | `modesetting` + glamor（DRI3） | 有了 panfrost 就不需要 `AccelMethod none` |
| 无 X 路径 | KMS/DRM 直出（ES、Ruffle Handheld 继续用） | **不能为了 X 把现有直出链路拆掉** |

**关键约束**：现有 ES / 模拟器 / Ruffle Handheld 全是 **KMS/DRM 直出**。
新底座必须**同时**保留直出和 X 两条路，X 只给 Chromium 和官方 Ruffle 桌面版用。
不要把所有东西塞进 X —— 1 GB 内存扛不住。

## D. 音频：ALSA 直出为默认，PipeWire 按需起

| 方案 | 常驻内存 | 适配 |
|---|---|---|
| **ALSA 直出** | 0 | ES、模拟器、Ruffle Handheld 本来就直连 ALSA ✅ |
| PulseAudio | ~25 MB | 老，Chromium 兼容好，但没必要 |
| **PipeWire + wireplumber** | ~35–50 MB | Chromium / 桌面 Ruffle 需要它 |

**方案**：默认只跑 ALSA（已实现，2026-11-14）；`chromium` / `ruffle-desktop` 的启动脚本里
`systemctl start --no-block pipewire` 再起进程，退出时 `stop`。
1 GB 机器上不为"可能用得到"的音频服务常驻 50 MB。

**必须修的既有坑**（`07_运行时架构` 第 6、7 条）：声卡被残留进程占住 → Rust panic → 看起来像黑屏。
新底座上这条要写进启动器：**起之前 `pkill -f 'runtime/ruffle-native'`**，已经是现成逻辑，直接搬。

## E. 迁移路径：三分区布局不变，只换 rootfs

### E.1 分区

| 分区 | 现在 | TreeOS | 动作 |
|---|---|---|---|
| BOOT (FAT32) | 内核 / dtb / boot.ini / logo | 保留 | 重写内容，**布局不变** |
| rootfs (ext4) | ArkOS 19.10 | Debian 13 | **整块替换**，容量可能需扩 |
| EASYROMS (exFAT) | 游戏 / 存档 / 游戏数据 | 保留 | **一个字节都不动** |

**结论：刷 TreeOS 不丢游戏、不丢存档。** 用户在 EASYROMS 里的东西全部原样。
根因是 glibc 的兼容是**单向的**：2.30 编的二进制能在 2.41 上跑（**但只解决 ABI 这一层**；实测 VLC 插件、wayland/libdrm 版本冲突都踩过，不能理解为"全部可搬"），
所以 **ES 二进制、模拟器核心、Ruffle Handheld 全部可以原样拷过去**，不用重编。
这是这条路能成立的最大前提。

### E.2 用户态迁移清单（按风险从低到高）

1. `/roms/**` — 不动
2. ES 二进制 + 主题 + `es_systems.cfg` / `.sd1`（两处都要）— 直接拷，回归验证
3. RetroArch 核心 — 直接拷，核心里有 GL 的要做一轮验证
4. `/opt/system/*.sh` 那 26 个菜单脚本 — 直接拷，逐个 `bash -n` + 冒烟
5. `/opt/rufflesa`、`ports/rufflehandheld`、`flash-new.sh`、`game-keys.service` — 直接拷
6. `zram-swap.service` — **必带**，1 GB 机器的保命件

### E.3 配置目录的一个坑

`/home/ark/.config` 里有一堆软链接和权限位。**exFAT 不存权限位和软链接**，
所以用户配置不能简单丢到 EASYROMS。做法：配置留在 rootfs，
升级时用 `tar` 打包到 `EASYROMS/.treeos/snapshots/`（tar 保留权限），回滚时解回来。

### E.4 OTA 怎么做（不做 A/B 双分区）

卡小、镜像大，A/B 不现实。用**单 rootfs + 快照回滚**：

```
升级包（tar.zst，只含变更文件 + 版本号 + sha256）
  → 校验 → 快照当前 /usr /opt /etc 到 EASYROMS/.treeos/snapshots/<旧版本>.tar.zst
  → 解包覆盖 → 重启
  → 起不来：菜单里有个"回滚到上一版本"，或 u-boot 里选 recovery
```

- **用户数据（存档/游戏）永不参与升级**（在 EASYROMS）
- 升级包按版本号只发增量，几十 MB 量级
- 这一层做完，**"热更新"就在新底座上重新成立**，之后不用再刷机

## G. 真机实测（2026-11-13，SSH 到 192.168.20.122）

> 下面全是**实测**，不是推断。之前文档里按"待验证"处理的条目，这里逐条给结论。

### G.1 分区与容量（原 A 节的最大不确定，已解）

| 分区 | 大小 | 已用 | 结论 |
|---|---|---|---|
| p1 BOOT | 256 MB vfat | 99 MB | 🟡 主线的 Image 更大（30–40 MB），**剩 154 MB，够，但没余量** |
| p2 rootfs | **11 GB** ext4 | 7.9 GB | ✅ Debian 3.5–5 GB 完全放得下，**不用重新分区** |
| p3 EASYROMS | **47 GB** exFAT | 2.8 GB | ✅ 原样保留 |

卡是 64 GB。**这意味着迁移可以"只换 p2 的内容"，分区表一个字节不用动**，
刷机助手的流程也不用改。

### G.2 设备树（原 B.3 的强线索 → 已确认，但结论要修正）

- 板级 compatible：`rockchip,rk3326-r36s-linux` + `rockchip,rk3326`
- **不是**直接兼容 `odroid-go3`，但 `boot.ini` 头是 `odroidgoa-uboot-config`，
  键位设备叫 `odroidgo3-keys` → **同源分叉**，主线 dts 不能直接套，要改。
- DSI 控制器 compatible：**`rockchip,px30-mipi-dsi`** → 主线 `dw-mipi-dsi-rockchip` 支持 ✅

**面板节点（可直接搬进主线 dts）：**

```
/dsi@ff450000/panel@0
  compatible = "simple-panel-dsi"      ← 主线 panel-simple 就有这个
  dsi,lanes = 4
  reset / delays / init-sequence 都在
  display-timings/original : 58 MHz, 640x480, 300/200/300 + 17/5/13 → 78 Hz
  display-timings/adjust   : 29 MHz, 640x480,  46/2/44  + 165/2/14 → 60 Hz
  尺寸 52×70 mm
/backlight  compatible = "pwm-backlight"，默认亮度 51
```

→ **但当天晚些时候查了 mainline 源码，这条判断被推翻了一半（见 G.8）。**
面板不是私有驱动，但**也不是拷过去就能用**：mainline 不认 `simple-panel-dsi`，
也不解析 `panel-init-sequence`。参数全部已知，缺的是一段驱动代码。

### G.3 图形（原 B.1 的判断得到证实）

```
Mali-G31 r0p0, 1 core（Bifrost, 0x7093）
/dev/mali0  ← 厂商 kbase 驱动，**编进 4.4 内核里**（/lib/modules 下没有 .ko）
/dev/dri/card0 + renderD128 + controlD64 都在
libEGL.so.1 / libGLESv2.so.2 → libmali-bifrost-g31-rxp0-wayland-gbm.so
```

两个结论：
1. **现在的 GL 全部来自厂商 blob**，Mesa 只是个壳。所以 `DRI3 error` 是必然的——
   libmali 不走 GBM/DRI3 那套。
2. blob 是 **wayland-gbm 版**，说明厂商本来准备了 GBM 路径，但内核 4.4 缺 `drm/panfrost`，
   新 Mesa 用不上。**换 6.1 内核后可以直接换成 Mesa panfrost**。

### G.4 音频（原 D 节的风险，已解）

```
card 0: rockchip,rk817-codec   ← RK817 PMIC 自带 codec
/rk817-sound: simple-audio-card, i2s, 带耳机检测 GPIO
```

主线 5.11+ 有 rk817 codec，6.1 内核直接支持。**这条不用自己写驱动。**
注意：实测 `Playback` 是 0%（-72 dB），出厂就是静音状态，新系统要设个默认值。

### G.5 WiFi（原 F.1 第 4 条，风险确认）

```
USB 0bda:8179 RTL8188EU，挂 1a40:0101 内部 hub
驱动：厂商外挂 rtl8188eu（RTW v5.13.3），不是内核自带的
```

主线 `rtl8xxxu` 对 8188EU 支持不完整；**新内核要么带外挂驱动（DKMS），要么换 mainline 支持的方案**。
这条仍然是 K2 的**中等风险**，但方法明确。

### G.6 系统现状

- Ubuntu 19.10 / glibc 2.30 / 内核 4.4.189 / 918 MB 可用内存 / zram 2 GB —— 与文档一致
- **Xorg + openbox 已经装好了**（第 16 节那轮留下的），新底座可以直接复用配置
- `/opt/system` 只有 16 项、11 个 `.sh`，`gamelist.xml` 只有 1.7 KB
  → **菜单层迁移的工作量比预想小得多**
- 没有 `lsusb`、没装 RetroArch 核心到 `/opt/system/cores`

### G.7 修订后的风险表

| 原风险 | 现在 |
|---|---|
| 卡容量不够 | ✅ 解除（64 GB / rootfs 11 GB） |
| 面板点亮不了 | 🟠 参数全拿到了，但**需要一段面板驱动**（见 G.8） |
| 音频没驱动 | ✅ 解除（rk817 主线支持） |
| WiFi | 🟠 保持（外挂驱动） |
| panfrost 挂不上 G31 | 🟡 待验（主线支持 G31，但要实测帧率） |
| Boot 分区不够 | ✅ 基本解除：自编 Image 15–25 MB，剩 154 MB 够用 |

### G.8 查 mainline 源码后的修正：面板需要驱动补丁

查了 v6.12 的三份源码，结论很硬：

| 事实 | 后果 |
|---|---|
| `panel-simple.c` 的 `dsi_of_match` 只有 7 个具体型号，**没有** `simple-panel-dsi` | 厂商 compatible 匹配不上，驱动不 probe |
| `panel-simple.c` 与 `dw-mipi-dsi-rockchip.c` **都不解析** `panel-init-sequence` | 初始化序列发不出去，黑屏 |
| `panel-sitronix-st7701.c` 已重构成结构化 desc（gamma/GIP），不接原始 DCS 序列 | 套不进现成驱动 |

**处置：写一个 ~330 行的独立面板驱动**（`dts/panel-r36s.c`），
其中 151 条初始化命令已从 dtb 自动解出来。这比把厂商序列硬塞进 st7701 干净得多，
而且补丁面小、好维护。

**这件事改变了 K2 的性质**：它不再只是"调 dts"，而是"带一个内核补丁"。
补丁本身很小，但它意味着 TreeOS 以后要自己扛一份内核补丁集——这是发行版必须付的成本，
不影响结论，但要在日程里算进去。
