## 总结论

**先做 v4 干净候选镜像，再用这张镜像完成存档与关机闭环；不要先重做配网页。** 但有两个发行前置条件不能被归类为“以后优化”：

- **确认低电量行为可控**：电量不显示可以暂缓，低电量导致无预警掉电、损坏存档不能接受。
- **审查 `sudo nmcli` 授权边界**：它是临时功能修复，不等于已具备发行级权限设计。

当前最缺的不是功能，而是证明：**从公开镜像刷出的新卡，在没有母卡遗留状态的情况下，能稳定完成游戏、存档、关机和恢复。** GBA 只在母卡上验证，不能算镜像发行验收通过。

## 1. 先干净镜像和闭环，还是先修已知问题？

**选择：v4 干净候选镜像 → 完整闭环。**

理由：

1. **先固定受测对象。** 母卡、v3、新刷卡配置不同，继续在母卡上修功能，容易得到“开发卡正常，用户卡失败”的结果。
2. **存档与关机属于数据安全主链路。** 配网页方向反了有十字键绕过，存档写空没有可接受的绕过。
3. **闭环会暴露更关键的问题。** 包括权限、挂载、RetroArch 配置覆盖、退出时写盘、关机时序和文件系统恢复。

建议把 v4 定义为 **RC，不立即发布**。先做以下最小集合：

- 清除个人数据，处理首次启动身份生成。
- 固化输入和联网临时方案，记录适用范围与风险。
- 保留可导出的启动、RetroArch、关机日志。
- 在新刷卡上完成闭环测试。

**只有以下问题应插队：**

- 正常关机不可靠；
- 已复现存档损坏；
- 低电量行为存在明显数据风险；
- 默认暴露凭据或高权限入口。

热重启可以暂缓，但必须明确提供“关机后重新按电源”的可靠路径，不能把不可用的重启入口继续当正常功能展示。

## 2. 配网页修法排序

| 排序 | 方案 | 判断 |
|---|---|---|
| 1 | **当前接受十字键** | 最小风险，直接支持本轮交付；页面明确提示“请使用十字键” |
| 2 | **修 ES 源码并重编** | 长期正确方向；修复范围可控，避免再维护一套配网系统 |
| 3 | **自写配网页** | 当前不做；不仅是方向键，还要处理密码输入、扫描、隐藏 SSID、失败提示、取消和权限 |

源码修复必须满足：

- 固定上游提交、补丁和构建依赖，能复现构建。
- 检查是该页面直接读取原始轴，还是通用输入抽象的问题。
- 回归主菜单、WiFi 页面、列表滚动、十字键和摇杆。
- **不要为修一个页面再次全局反转轴。**

首次开机引导应等联网后端与权限方案稳定后再做，否则只是把现有缺陷搬到新页面。

## 3. 如何重复验证存档不会再次写空？

**有限测试不能证明“永不写空”；可以证明特定镜像、核心和故障条件下，没有观察到损坏，并且覆盖了主要失效路径。**

“关闭排序＋放内容目录”只是配置，不是根因证明。先分清：

- 游戏内存档：SRAM/Flash 等持久化文件；
- 即时存档：save state。

两类必须分开验收，不能用即时读档成功证明游戏内存档可靠。

### A. 固定测试条件

记录：

- 镜像 SHA-256、内核、RetroArch、核心版本；
- ROM 哈希及合法来源；
- RetroArch 最终生效配置，包括核心/目录/游戏覆盖；
- 实际存档路径、挂载类型、权限、剩余空间；
- 核心是否支持并实际执行 SRAM 自动保存。

至少选 **2 款采用不同存档类型的 GBA 游戏**。先覆盖主打核心，不要一次铺开所有模拟器。

### B. 建立可识别的存档标记

每轮在游戏里形成能辨认的进度，例如存档槽、角色名、关卡或游戏内计数；记录为 A、B、C。

每个检查点保存：

- 存档文件路径、大小、SHA-256；
- 独立备份；
- 游戏内实际读出的进度。

**文件非零不代表有效，哈希变化也不代表正确，必须结合游戏内读取验证。**

### C. 测试矩阵

| 场景 | 验收要求 |
|---|---|
| 游戏内保存 → 正常退出 → 再进游戏 | 最新进度可读 |
| 保存 → 退出 → ES 关机 → 完全断电 → 冷启动 | 最新进度可读 |
| 连续反复进入、退出同一游戏 | 不被空文件或旧文件覆盖 |
| 存档目录只读、空间不足 | 有明确失败信号，原有有效存档不应被破坏 |
| 已知旧存档 → 保存新进度 → 不同时间点断电 | 至少能判断保留旧进度、新进度还是损坏，并记录概率 |

建议最低执行量：**两张不同卡，每张 20 次正常闭环；另用测试卡做不少于 20 次分时点断电测试。** 这是工程门槛，不是可靠性统计保证。

断电测试要区分“保存尚未落盘”和“写盘期间”。不能要求保存后立刻断电仍然零丢失；应定义可接受边界：

> 正常退出、正常关机必须保留最新存档；异常断电允许损失尚未持久化的进度，但不得出现持续、静默覆盖已知有效存档的行为。

### D. 如果复现写空，先定位再改配置

重点检查：

- 核心是否先加载存档失败，随后退出时把空 SRAM 写回；
- 存档路径是否因配置覆盖而改变；
- 是否存在多个进程或脚本写同一个文件；
- 退出方式是否跳过核心保存；
- 文件更新是否直接截断原文件，是否使用临时文件、同步和原子替换。

**事后跑一次 `sync` 不能修复“应用已经写入空内容”的问题。** 自动备份也必须保留上一版已知有效副本，不能无条件用最新文件覆盖。

## 4. 是否提供 6–8 GiB 精简版？

**值得，但优先做一个小容量标准镜像，不要立即维护大小两条产品线。**

2.6 MB/s 下，写入 6–8 GiB 约需 **41–55 分钟**，仍慢，但明显优于 110 分钟。容量应由实际文件占用、升级余量和扩容设计决定，不要硬凑 6 GiB。

推荐：

1. 去掉个人数据、包缓存、日志、无用缓存和不应分发的 ROM。
2. 缩小文件系统和分区，生成真正较小的磁盘镜像。
3. 首次开机自动扩展承载用户数据的末尾分区与文件系统，状态可见、失败可重试。
4. ROM/存档目录保持稳定，扩容后自动获得剩余空间。

**压缩镜像只减少下载量，不会自动减少解压后需要写入 SD 卡的字节数。**

另外：

- 最小卡规格必须用实际卡验证；“16 GB 卡”未必能容纳“16 GiB 镜像”。
- 首启扩容完成前不要启动会写入用户数据的前端。
- 若用 GPT，需正确处理备份 GPT 位置；若用 MBR，则按实际布局验证，不能照搬 GPT 流程。
- 零填充空闲空间改善压缩率，但不等于缩小 raw 镜像。

## 5. 发行前还缺哪些可交付要素？

### P0：公开测试版前必须补齐

**镜像卫生与身份**

- 删除 WiFi 配置、用户 SSH 私钥、未经授权的 `authorized_keys`、历史、令牌、个人缓存。
- SSH host key 不应克隆给所有设备：首次启动生成唯一密钥。
- 正确处理 `machine-id` 和随机种子，避免克隆身份。
- 明确 SSH 是否默认开启、登录方式和默认账号策略。

**联网权限**

- 给出实际 sudoers 规则并做审查。
- `sudo /usr/bin/nmcli "$@"` 是开放 root 执行 nmcli 的入口，不只是“允许连接 WiFi”。
- 优先考虑受限 polkit 授权；若暂用包装器，应限定调用用户、操作范围，并确保脚本和目录不可被普通用户修改。

**刷写与介质验证**

- 防止自动挂载干扰，并确认目标设备。
- 卸载、写入、刷新、离线回读校验，再首次启动。
- **第 1 扇区和第 64 扇区检查只能算局部检查，不是镜像完整性验证。**
- 回读比较应在首次启动修改文件系统、扩容之前进行。
- 清盘时考虑盘尾残留签名；写前 32 MiB 零不等于完整清除盘尾 GPT。

**验收与恢复**

- 两张不同品牌/型号的卡完成新刷验收。
- 正常关机、冷启动、存档和低电量行为验证。
- 实做救援：系统无法启动时，能否取回存档、重刷、恢复并读档。
- 验证备份确实能恢复，而不是只确认生成了备份文件。

### P1：版本交付材料

- 版本号、变更记录、已知问题和支持硬件范围；
- 镜像 SHA-256、构建配置、补丁及依赖版本；
- 首次开机、扩容等待、联网、关机、备份和救援说明；
- 日志导出方式，默认不泄露密码；
- GPL 等许可证对应源码及其他分发义务；
- 不随镜像分发未获授权的游戏、BIOS 等内容。

## 6. 最可能翻车的三条

### 1. 母卡能保存，新刷卡却丢档

**风险最高。** 配置覆盖、路径、权限、核心退出和关机时序尚未经过镜像级验证。

**措施：** 只认新刷 v4 的测试结果，实施上述存档矩阵，并保留出错前后的文件和日志。

### 2. 卡刷得出来，但交付过程不可靠

已有自动挂载、残留分区信息和超慢写入案例；目前局部扇区校验不足以证明整卡写入正确。

**措施：** 小镜像、完整回读、多卡测试、首启扩容验证和真实救援演练。

### 3. 正常运行结束阶段出事故

低电量状态不明、关机路径未充分证明、用户因黑屏或重启无效而强制断电，最终表现为“系统坏了、存档没了”。

**措施：** 优先验证关机和低电量保护；重启不可用则暂时隐藏或明确标注，不得诱导用户反复硬断电。

个人凭据泄露和过宽 sudo 授权则是**独立的发行阻断项**，不能因为不在上述故障概率前三就放过。

## 对现有计划的调整

建议改为：

1. **v4 RC：清洁镜像、身份初始化、权限审查、固定配置。**
2. **新刷卡验收：存档、正常关机、冷启动、低电量、扩容。**
3. **多卡与故障验证：断电测试、完整回读、救援恢复。**
4. **最低性能基线：帧时间/音频卡顿、温度与降频；不只看平均 FPS。**
5. **ES 配网页源码修复，再做首次引导。**
6. **OTA、主题、更多模拟器继续后置。**

**当前发布门槛应是“新卡可复现、存档可信、故障可恢复”，不是“菜单功能齐全”。**
