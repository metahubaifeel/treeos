## 总评

**当前定位应是“单机硬件适配成功的开发原型”，不是发行版候选版本。** 真机跑通显示、音频、输入和 GBA，已经证明路线可行；但**干净部署、持久化可靠性、电源管理、可复现构建**还没有闭环。

你们的路线大体正确，但需要三处调整：

1. **新卡验收必须包含“再次开机后读回存档”，不能以关机结束。**
2. **救援和数据备份前移，早于大规模清理脚本。**
3. **热重启故障、存档写空、电池状态缺失不能视作体验问题：分别涉及更新恢复、数据可靠性、供电安全。**

此外，报告中有几项“已解决”其实只是“绕过或恢复现场”，不能关单。

# 一、交付优先级：同意新卡验收，但验收闭环不完整

你们提出的：

> 新卡刷 v3 → 开机 → 玩 GBA → 存档 → 关机，全程无电脑

方向正确，应该改为：

> **校验镜像 → 刷写并回读校验 → 首次启动 → 游戏 → 游戏内存档 → 正常退出 → 掌机按键关机 → 再次开机 → 读回存档 → 再运行游戏。**

其中必须区分：

- **游戏内存档**：SRAM、EEPROM、Flash 等，经核心落盘。
- **即时存档**：RetroArch save state。
- 两种都要验证，**优先保障游戏内存档**；即时存档对核心版本更敏感。

### 开始验收前的必要条件

1. **母卡备份完成，且验证可读取。** 不要在唯一能启动的卡上继续做破坏性操作。
2. 固定 v3 镜像及完整 SHA-256，后续修复产生 v4，不覆盖同名文件。
3. 明确最低支持卡容量，依据是**实际扇区数**，不是“16GB”标签。
4. 确认镜像内没有构建机残留的分区 UUID、第二张卡依赖、个人目录路径、SSH 私钥等。
5. 验证最终启动入口确实使用镜像内的内核、DTB 和 rootfs，而不是偶然使用母卡遗留文件。

### 建议最低验收矩阵

| 项目 | 最低要求 |
|---|---|
| 新卡 | 两张不同型号、质量可靠的卡 |
| 启动 | 每张至少 10 次冷启动，无首次启动手工修复 |
| 持久化 | 多次保存、退出、关机、重新开机后内容正确 |
| 离线 | 无网络、无 SSH、无开发机挂载也能完成主要操作 |
| 双卡 | 缺少第二张卡时不挂死；若支持第二张卡，验证枚举变化 |
| 容量 | 最小支持卡能刷入；大卡扩容正确且不破坏数据 |
| 日志 | 无持续 I/O 错误、文件系统错误、OOM、GPU hang |
| 音频输入 | 耳机插拔、退出游戏、再次进入后均正常 |

“全程无电脑”是用户体验标准，不妨碍你们通过串口采集日志。**不能用 SSH 补配置让验收通过。**

# 二、GBA 36fps：先确认测量和渲染路径，再调 governor

## 先纠正数据口径

你们列的：

> 12 秒 515 帧

直接相除约为 **42.9 fps**，不是 36fps。两组结果可能来自不同测试，但目前不可比较。

GBA 正常速度约为 **59.73 fps**。必须同时区分：

- 核心运行速度；
- 视频呈现帧率；
- 是否启用跳帧；
- 音频是否断续、变慢；
- 实际墙钟时间。

**RA 显示的一个 FPS 数字不能单独证明模拟速度。**

## 推荐排查顺序

### 1. 固定测试条件，建立干净配置

固定：

- 同一个 ROM，并记录哈希；分发时注意版权；
- 同一段游戏流程；
- RetroArch 版本、核心版本或 commit；
- 内核、DTB、Mesa、架构、视频和音频后端；
- 电池/供电状态及温度。

不要直接在 ArkOS 迁移来的全局配置上调参。使用独立配置运行，暂时关闭：

- shader；
- rewind；
- run-ahead；
- recording；
- overlay；
- 帧延迟和自动帧延迟；
- 黑帧插入等功能。

排除 override、核心配置、游戏配置再次覆盖设置。

### 2. 确认真正使用 GPU，而非软件渲染

从 RetroArch verbose 日志核对：

- 视频驱动与 context；
- EGL/GLES renderer；
- 是否为 Mali/Panfrost，而非 `llvmpipe`、`softpipe`；
- 最终加载的核心路径；
- 最终加载的音频驱动。

“系统能报告 GLES 3.1”**不等于游戏进程正在使用该加速路径**。

### 3. 检查 CPU 频率、限频和单核瓶颈

记录负载下：

- 每核利用率；
- 实际频率及 cpufreq policy；
- 温度、thermal throttling；
- 电源模式；
- 频繁的后台任务。

短时间切换 `performance` governor 做对照可以，**不要直接把它作为量产解决方案**。GPU 正常不代表 gpSP 的 CPU 执行正常。

### 4. 验证 gpSP 构建和动态重编译器

这是高优先级项：

- 用户态到底是 armhf 还是 arm64？
- 核心二进制实际是什么架构？
- 当前 gpSP 构建是否支持并启用对应架构的 dynarec？
- 是否因构建选项或执行内存权限等原因退回解释执行？

**不要把“换成 Debian RetroArch”与“核心也正确且高性能”混为一谈。**

### 5. 核对 DRM 实际刷新率及同步阻塞

自写面板驱动意味着这一层不能跳过：

- DRM mode 的 pixel clock、横纵总时序是否对应目标刷新率；
- 实际 vblank 周期是否正确；
- 是否存在 page flip 超时；
- RA 的刷新率设置是否与实际模式一致。

640×480 只是分辨率，不证明是 60Hz。

### 6. 单变量测试音频、视频同步和线程视频

依次做诊断性对照：

- 关闭音频同步；
- 暂停音频输出；
- 关闭视频垂直同步；
- 线程视频开/关。

每次只改一项，记录游戏速度、声音、CPU 和帧时间。**关闭同步后变快只说明受同步链路限制，不代表修好了。**

最后再对比另一个核心，判断是 gpSP 特有问题还是系统公共路径问题。

## 关于已有基线

**我没有可核验的、与你们“主线 6.12 + Mesa 25 + Debian RA 1.20 + 指定 gpSP 构建”完全匹配的 RK3326 基线，不能给出可信的现成数字。**

合理目标是：选定兼容性正常的 GBA 样本，在不开高级效果时达到接近原速、音频连续。RK3326 跑 gpSP 不应把持续 36fps 当正常能力边界，但仍需靠上述测试定位，不能承诺所有游戏。

# 三、84 个 ArkOS 脚本：要收敛，但不要按数量清理

**84 个脚本放在磁盘上，不等于存在启动或内存开销。** 真正的问题是：哪些会执行、谁调用、具有什么权限、修改什么状态。

先建立清单：

| 分类 | 处理方式 |
|---|---|
| 启动链、按键、电源、挂载 | 优先审计，不贸然删除 |
| 更新、分区、修复、超频工具 | 默认禁用或移出菜单，防止误操作 |
| ES/RA 正在调用的启动器 | 保留，补测试 |
| 没有调用入口的遗留项 | 隔离，观察后删除 |
| 下载执行、修改库路径、硬编码设备名 | 高风险，优先处理 |

特别搜索：

- `LD_LIBRARY_PATH`、`LD_PRELOAD`；
- `/dev/mmcblk0` 等硬编码；
- `dd`、`mkfs`、`parted`；
- 直接覆盖 `/boot`；
- `curl ... | sh`；
- 杀进程、修改音量/CPU、后台死循环。

### 是否改为 systemd + Python？

**选择性替换，不要开展整套重写。**

- 常驻服务、重启策略、启动依赖：systemd。
- 简短命令包装、启动游戏：shell 足够。
- 复杂配置、校验、结构化数据处理：Python 合适。
- 用户交互工具：根据现有 UI 集成方式选型。

systemd 单元不能替代全部业务逻辑。先冻结行为和接口，再替换实现，否则容易把目前能玩的系统重新拆坏。

# 四、OTA：当前先做可恢复发行，不先做在线更新

你们的数据有歧义：

- 镜像写“16 GiB”；
- 问题中又写“7.5 GiB 镜像 + 11 GiB rootfs”。

这可能分别指原始镜像、压缩文件、分区容量或已用空间。**压缩包大小不能用于判断 A/B 是否放得下。**

先提供：

- 总扇区数和分区表；
- 各分区容量；
- rootfs 已用空间；
- `/boot` 所在位置；
- 用户数据和 ROM 所在位置；
- bootloader 可用的启动选择、失败回退机制。

## 当前建议

**短期：整卡发行 + 独立数据备份 + 可验证的重刷恢复。**

如果目标是“rootfs 坏了，15 分钟恢复”，先证明：

> 另一张卡能启动 → 取回或保留用户数据 → 重刷系统 → 恢复存档和配置。

目前只有整卡镜像还不够。它能恢复旧状态，但也可能把用户后续存档一起覆盖。

### A/B 与 recovery 的边界

**A/B 更适合无人值守更新回退，但前提更重：**

- 两份系统槽位；
- 内核、DTB、必要模块与 rootfs 成套匹配；
- 非活动槽写入并校验；
- 有限次数试启动；
- 健康检查后才确认；
- 启动失败能自动回退；
- 用户数据格式升级保持可回退兼容。

**recovery 更节省空间，但不自动等于断电安全。**

如果恢复环境也依赖被更新的内核、DTB、启动分区，rootfs 之外的故障仍可能让 recovery 一起失效。它必须有独立且已验证的启动入口。

### 必须明确的限制

**同一张消费级 SD 卡上的 A/B 不能保证抵御所有断电损坏。** 卡内部 FTL、控制器和共享启动区域都可能成为共同故障点。

因此，对外只能承诺经过测试的故障模型，不能笼统说“断电保证恢复”。在实现、刷卡和失败注入验证前，不要上线 OTA。

# 五、1GB 内存：暂不调大 zram，先证明有内存瓶颈

477.8 MiB zram 是**逻辑交换容量**，不是预先占掉约 478 MiB RAM。实际占用取决于写入量、压缩率及元数据。

对 GBA 来说，持续掉到 36fps，**不应先怀疑 zram 太小**。

### 先测这些

- `MemAvailable`；
- zram 的 `orig_data_size`、`compr_data_size`、`mem_used_total`；
- `vmstat` 的换入换出；
- `/proc/pressure/memory`；
- OOM 日志；
- 游戏时 ES 是否仍占用明显内存。

### 建议起点

- 先维持约 512 MiB zram。
- 使用低开销算法作为基线，具体以目标内核支持和实测为准。
- `swappiness` 可先以 **100** 为测试起点，对照 60、100、150；这不是 RK3326 特效参数。
- 不建议为游戏场景增加持续写 SD 卡的 swap 兜底。

若正常游戏期间持续压缩、换入换出，优先减少后台常驻和资源占用，不是一直扩大 zram。

### N64 / PSP

- **N64：可以作为按游戏验证的功能，不能承诺全库。** 核心、RSP、图形插件及游戏差异很大。
- **PSP：可以验证轻负载标题；RK3326 不能承诺普遍全速。** 优先原生 PSP 分辨率、关闭增强、固定渲染后端测试。
- 不要以跳帧后的显示数字冒充全速，也不要以更多 zram 解决 CPU/GPU 性能不足。

**Chromium 建议从当前发行目标移除，而不仅是排最后。** 它会扩大内存、存储、安全更新和 UI 适配范围。

# 六、最可能翻车的地方：按优先级排列

## P0：存档“恢复了”，但根因没有被证明修复

> “被 RA 写空 → 关 sort_savefiles → 从备份恢复”

这不足以证明因果。`sort_savefiles` 主要影响目录组织，**不能据此解释为什么文件被截断**。

需要排查：

- 是否实际写到了另一条路径；
- 不同核心、不同同名 ROM 是否覆盖同一文件；
- 权限、满盘、I/O 错误；
- 核心退出时是否正常 flush；
- ES 是否强杀 RA；
- 是否同时启动多个 RA 实例；
- 核心需要的 SRAM 大小是否一致。

**在反复保存、退出、重启验证前，存档可靠性不得标绿。**

## P0：电池管理不只是显示百分比

需要验证：

- 电压、充电状态、低电阈值；
- 低电时能否完成保存和正常关机；
- 充电插拔、边充边玩时温度；
- 关机后是否确实进入预期电源状态。

RK817 存在不等于整机电源管理已正确。**不能让用户依靠突然掉电结束游戏。**

## P0：镜像及卡容量不匹配

标称同容量 SD 卡扇区数可能不同。若镜像按整张母卡末尾构建，新卡可能刷不下。

同时防止：

- 首启扩容中断后无法再次启动；
- fstab 使用不稳定设备编号；
- 两卡 UUID 重复导致挂载错误；
- 只备份 rootfs，却遗漏启动所需区域。

## P1：热重启没有解决，只是绕过

“改为关机再开”可作为开发阶段说明，**不能算修复**。

它会影响更新、故障恢复和看门狗。串口需要确认卡在哪里：

- reset 到 BootROM；
- DDR 初始化；
- U-Boot；
- SD 初始化；
- 内核加载。

既然报告称卡在 U-Boot 阶段，就不能直接归咎 Linux；也不能排除 Linux 退出后遗留的硬件状态。先用串口确定边界，再做复位/断电对照。

## P1：R36S 不是唯一硬件配置

市场上同名设备可能存在面板、板型及外设差异。

目前应写成：

> 支持已验证的某 PCB / 某面板版本。

151 条面板初始化命令需记录来源、许可和适配范围。“主线 6.12”也应明确是**基于主线、带自有补丁**，不能暗示整机已获上游支持。

## P1：开发环境污染尚未完全排除

`unset LD_LIBRARY_PATH` 是线索，不是完整修复。还应检查：

- `/etc/ld.so.conf.d/`；
- `/usr/local/lib`；
- RPATH/RUNPATH；
- 启动脚本和用户环境；
- 混装包及手工复制的库。

真正的验证是：**干净构建的新卡也能运行，而不是母卡碰巧能运行。**

## P1：padmerge 的键盘方案存在生命周期风险

需要验证：

- RA 内快捷键是否和普通按键冲突；
- 轴抖动、死区、方向释放是否正确；
- RA 崩溃或 padmerge 重启后是否卡键；
- 原物理设备和虚拟设备是否造成双输入；
- ES、RA 是否争用设备。

长期可评估统一虚拟 gamepad，但不必阻塞第一版；先把现有方案的边界测清。

## P1：有源码仓库，不等于可重现发行

至少保留：

- 内核与 U-Boot 来源、commit、补丁；
- DTB、配置和工具链版本；
- Debian 包版本及软件源快照；
- RA 和核心的来源；
- 完整镜像构建日志；
- 发行许可证与源码提供方式。

`olddefconfig` 漏 `ARCH` 应通过构建脚本强制设置、产物架构检查及失败退出解决，不能继续靠人工记忆。

# 建议修订后的路线

1. **完成母卡备份，冻结 v3。**
2. **新卡完成“首次启动—保存—关机—再次读回”闭环。**
3. **并行处理存档根因、正常关机、低电行为及热重启定位。**
4. **建立 GBA 可重复基准，解决性能问题。**
5. **建立存档导出/恢复和重刷恢复流程，实际演练。**
6. **按调用关系审计并逐步收敛遗留工具。**
7. **达到候选版标准后再设计 OTA。**

**第一版的目标不是功能多，而是：明确支持哪台机器、干净卡能启动、游戏速度正常、存档不会丢、用户能安全关机、坏了能恢复。这六件事没有闭环之前，不要扩展 Chromium、超频和复杂 OTA。**
