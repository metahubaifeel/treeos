## 总评

**方向可行，实施顺序基本正确，但目前还不具备“三项改完、替换二进制就发镜像”的条件。**

建议决策：

- **同一个 fork 维护 D16/N3/N10：可以。一次性合并后才验证：不可以。**
- **D16 是优先修复项；N3 是独立增强项；N10 应先确定用户任务和入口映射，再改代码。**
- **设备原生编译适合第一次打通；长期应迁到固定环境的 PC 交叉构建。**
- **v4 作为未改 ES 的恢复基线保留，新 ES 进入下一测试版本，不覆盖唯一基线。**

以下是基于方案的设计评审，**不等于已经审过该仓库实际实现**。尤其 D16 的事件分发和 N3 的布局 API，需要在源码中确认。

## 1. 一次 fork 同时改 D16/N3/N10：风险和顺序

### 一个 fork 合理，“一次编译解决三个问题”不合理

方案开头写“一次编译”，实施步骤却要求逐项构建。**应以逐项构建为准。**

推荐提交与测试顺序：

| 阶段 | 内容 | 放行条件 |
|---|---|---|
| B0 | 固定上游提交，不做功能修改 | 构建成功，启动、进游戏、退出游戏、设置保存正常 |
| B1 | 仅 D16 | 键盘导航回归通过 |
| B2 | 加 N3 | 主题页布局、切换、保存/取消正常 |
| B3 | 加 N10 | 所有旧入口都有明确去处，限制模式不被绕过 |
| RC | 打包进镜像 | 首启、重启、恢复及长时间运行测试通过 |

每阶段保留 **Git commit、构建日志、二进制校验值、安装包和测试记录**。`/tmp/es-src` 与压缩包只能当工作副本，不能当源码管理。

### D16 补丁方向合理，但现在不能判定已经修对

当前补丁存在几个必须核实的前提：

1. **`kbUs[0].size()` 是否等于当前行的实际可导航宽度？**  
   空格、确认、退格等键可能跨列；某些格子可能没有可聚焦组件。第一行的列数不一定代表每行有效边界。

2. **`curCursor.x() == 0` 是否真表示最左侧可选键？**  
   若网格有空列、跨列或禁用单元，这个判断会失效。

3. **事件是否只在按下时处理？**  
   如果外层没有过滤 `input.value`，按下与释放都可能触发导航。不能只看这段代码下结论。

4. **非边缘分支是否真的交给网格处理？**  
   需检查后续 `return` 和父组件事件分发；否则可能由“跳反边”变成“不动”。

5. **改的是所有文本键盘，不只是 WiFi。**  
   搜索、改名、刮削输入等入口都可能受影响。

最低测试集：

- 每一行从左到右、从右到左；
- 首尾循环、上下切换；
- 空格/退格/确认等特殊键；
- 短按、长按、快速交替；
- 十字键与摇杆；
- WiFi 密码输入、普通搜索输入。

**更稳的实现是基于实际可聚焦单元或网格导航接口处理边界，而不是把第一行字符串长度当作导航规则。** 如果查明网格本身已有正确循环导航，直接移除错误的手工跳转可能比新增边界逻辑更简单。

## 2. `preview.png + ImageComponent`：可行，但不是“加一张图”那么简单

### 可行，而且适合作为第一版

采用静态截图、不实例化整套主题，是正确取舍。RK3326、1GB 内存设备上，**不要为了预览启动完整主题渲染、视频和额外资源加载**。

但当前方案漏了以下工程细节。

### 必须处理的事项

- **布局**  
  `addWithLabel()` 后面追加组件，不代表设置页会自动给图片留高度。要确认 `GuiSettings`/列表组件是否支持带明确尺寸的自定义行，否则会覆盖、裁切或无法滚动。

- **不要写死 400×300**  
  按实际内容区计算尺寸，保持宽高比、限制高度。至少验证设备所有目标分辨率及中文字体下的显示。

- **初始化与回调生命周期**  
  页面打开时主动显示当前主题预览；不要只依赖选择变化回调。回调不能持有已销毁页面对象，也不能覆盖该控件已有的重要回调。

- **预览不等于应用**  
  切换候选项只更新图片；保存后才应用主题。取消不能改变当前主题。

- **资源限制**  
  不要把所有主题大图一起加载。缺图、损坏图、过大图都应能退化到占位状态，不能崩溃。图片源文件也应预先缩小，不能只缩小显示尺寸。

- **截图只是代表效果**  
  不同主题子样式、屏幕比例、系统页面可能差别很大。第一版标明“示意图”即可，不必马上实现每个变体的预览。

### 有没有更简单、更稳的方式？

**更简单的产品方案：专门做一个“主题选择”页。**

页面只包括：

> 主题名称列表 / 当前选中项截图 / 应用 / 返回

它比把大图片塞进通用 UI 设置页更容易控制尺寸、焦点和保存逻辑，也与 N10 的顶层“主题”入口一致。若现有设置页已经原生支持图片行，复用更省代码；否则不要为省一个页面去扭曲通用设置布局。

资源路径建议：

- 内置主题：主题目录内放 `preview.png`；
- 如主题目录由下载器或更新器管理：允许从 TreeOS 独立预览目录读取，避免更新主题把截图删掉；
- 缺失时使用内置占位资源或文字。

**第一版手工挑选并压缩几张截图即可，不必先做逐主题自动截图系统。**

## 3. 主菜单重排：目前缺的是任务映射，不是条目数量

“游戏库 / 主题 / 设置 / 工具 / 电源”可以成立，但**五项以内不是验收标准**。当前方案存在明显不一致：

- 表格仍保留 UI、声音等多个顶层入口，目标结构却只有五项；
- `GAME COLLECTION SETTINGS` 通常只是集合管理，直接改名“游戏库”会扩大含义；
- “系统设置”“设置”“高级设置”“工具”边界没有定义；
- “隐藏”与“迁移”混在一起，可能把必要功能直接藏没。

建议采用以下任务映射：

| 顶层 | 至少应覆盖 |
|---|---|
| 游戏库 | 更新游戏列表、集合管理、搜索/筛选入口或指引、封面与元数据刮削 |
| 主题 | 选择、预览、应用；必要的主题变体设置 |
| 设置 | WiFi、声音、亮度、语言、输入映射、界面行为、系统信息 |
| 工具 | 文件维护、诊断、备份/恢复、必要的高级维护功能 |
| 电源 | 关机、重启；有可靠实现才提供休眠 |

另外必须明确：

- 下载、主题安装、系统更新放哪里；
- 蓝牙、音频输出等设备已有能力不能因重排丢失；
- 外接手柄配置与恢复误配置的入口；
- 版本、剩余空间、IP 地址、故障日志如何查看；
- 退出 ES、重启 ES 与关机是否需要区分；
- kiosk/kid 等限制模式是否仍有效。

**刮削不建议默认当“高级功能”隐藏，它是整理游戏库的常见任务。**

`TreeOSAdvancedMenu=false` 只能控制高级维护项，不能把联网、输入配置、更新等正常任务一起隐藏。高级开关本身也必须有可发现的入口。

中文翻译还要核实：修改 `.po` 后，构建/安装流程是否生成并部署了运行时使用的 `.mo`。只改 `.po` 不一定生效。

## 4. 原生编译 vs PC 交叉编译

### 结论：首次原生，长期交叉

| 方式 | 适合用途 | 主要问题 |
|---|---|---|
| 设备原生编译 | 首次确认依赖、运行 ABI、快速验证 | 慢、内存紧、污染设备、消耗 SD 写入、难重复 |
| PC 交叉编译 | 日常开发、自动构建、发布 | 需要维护匹配目标环境的 sysroot 和工具链 |

原生构建并不自动等于“环境完全一致”：`apt install` 可能引入新版本库、替换兼容库或改变目标环境。

建议：

1. 在**独立开发卡/克隆卡**上做原生基线，不在待发布的干净卡上装编译工具；
2. 记录架构、发行版、编译器、CMake 参数、依赖版本及最终动态链接结果；
3. 从固定目标根文件系统整理 sysroot；
4. PC 使用固定工具链和容器构建；
5. 所有发布产物仍在真机上冒烟测试。

上游有 `toolchain-aarch64.cmake` 只能说明提供了交叉入口，**不能证明它适配 TreeOS 的 Debian、VLC、Mali/EGL 组合**。

`make -j1` 合理，但“10–20 分钟”没有实测支撑。zram 压缩能力依赖负载，477MB zram 不能按额外 477MB 物理内存计算。编译建议退出 ES，并监控内存、温度、磁盘空间和 OOM 日志。

## 5. 还没充分考虑的问题

### A. 基线源码未必对应当前已安装二进制

“未修改源码编译成功”不代表“恢复原版”。

先固定：

- 上游 commit；
- 当前二进制来源与版本；
- 原有补丁、构建选项；
- 运行时资源目录和启动脚本。

否则基线阶段就可能悄悄引入一批与 D16/N3/N10 无关的变化。

### B. 只备份二进制不够回滚

新版本可能修改设置文件、资源、翻译或主题状态。旧二进制未必能读新状态。

至少备份：

- ES 二进制及所需资源；
- 相关配置；
- 启动脚本/环境变量；
- 包版本和安装清单。

推荐做一个**带版本号的 `.deb`**，或版本化目录加受控切换。停止 ES 后安装，避免直接覆盖正在执行的文件；保留通过 SSH/控制台恢复的方法。

### C. 动态库、RPATH 和资源是交付的一部分

验证 `ldd`、`readelf` 输出，检查：

- 是否误链接开发环境路径；
- 是否引入目标镜像不存在的新库版本；
- 是否依赖启动脚本设置的 `LD_LIBRARY_PATH`；
- 字体、占位图、翻译、着色器等是否正确安装。

“在源码目录能启动”不能作为安装成功的证明。

### D. 128G 卡验证还缺首启扩容与断电场景

16 GiB 镜像写入 128G 卡后，要检查：

- 剩余空间是否按预期扩容；
- 扩容过程断电后能否恢复；
- 第二次启动是否稳定；
- 最小目标容量卡是否容得下镜像；
- 写入后读回校验及文件系统状态。

128G 卡刷写预计 1.5 小时，应分别记录**实际写入量、写入和校验耗时**，排除读卡器、连接或卡异常，不能只看“刷完”。

### E. 清理镜像后还需做“身份与访问”验收

现有清理方向正确，但还要检查：

- `/var/lib/dbus/machine-id` 与 systemd machine-id 初始化关系；
- SSH host key 生成发生在 SSH 服务启动之前；
- 删除的是 host key 还是也包含用户授权密钥，默认远程访问策略是什么；
- WiFi 配置是否在其他网络管理器、脚本、备份里残留；
- 默认密码、自动登录、配网页服务的监听范围与退出行为。

**没有旧凭据，不等于默认安全。**

### F. 电量修复需要验证失败路径

`CONFIG_CHARGER_RK817=y` 加文件输出，只证明链路建立，不代表电量逻辑完整。

要测：

- 启动时文件尚不存在；
- 服务异常或数据过期；
- 充电、满电、低电量；
- 文件更新是否原子化，是否可能读到空文件；
- ES 是否正确显示未知值，而不是错误显示 0%；
- 低电关机是否另有可靠机制。

## 建议立即执行

1. **保留 v4 干净镜像及完整 SHA-256，不在其上装开发依赖。**
2. 建立持久 Git 仓库，固定上游提交，拆开 D16/N3/N10。
3. 开发卡完成未修改源码的构建、安装和运行基线。
4. 优先验证 D16 的网格与输入事件假设，完成单独回归。
5. N3 先做静态单图预览；N10 先产出完整的“旧入口 → 新入口”表。
6. 用版本化安装包交付，验证配置回滚与无图形界面恢复。
7. 最后生成新镜像，完成首启、扩容、重启、游戏启动退出和异常恢复验收。

**当前最值得阻止的不是“一个 fork 改三项”，而是没有固定基线、没有任务迁移表、没有完整回滚，却把三个功能一起装进发布镜像。**
