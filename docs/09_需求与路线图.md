## 二、新增需求（2026-11-14）

### N1 · 配网向导（类似 MiraLight）

- 开机进不了网时，**自动开热点**
- 手机连上热点 → 打开网页配置 Wi-Fi
- 同时提供：**控制台入口**（网页终端 / SSH 开关）
- 目标：用户不需要插键盘、不需要懂 Linux

### N2 · 摇杆测试

- 系统内置一个"按键/摇杆测试"页面（参考 ROCKNIX）
- 显示每个按键、摇杆轴、扳机值
- 用途：验机、排查漂移
- ✅ **2026-11-15：ES 自带 JOYPAD TEST / 死区 / 校准**（ArkOS 血统），不用开发；
  详见 `10_其他系统值得抄的功能.md`

### N3 · 主题一键切换 + 预览

- **兼容社区 ES 主题**（不只自家 Tree）
- 列表里能**预览截图**，选中即切
- 不许让用户拷文件、连电脑
- **2026-11-15 补充（拙木原话）**：移动光标到某个主题时，要能**预览实际效果**，
  不能只有文字列表（"只有文字太奇怪了"）；选中前先看到长什么样再决定
- **实现方案（2026-11-16 补）**：
  1. **推荐：预生成预览图**——用 ES 依次加载每个主题，截一张系统列表页（640×480），
     存为 `/roms/themes/<theme>/preview.png`
  2. 修改 ES 源码的主题选择页：光标移动到主题时，右侧显示该主题的 `preview.png`
  3. 没有预览图的主题显示占位图 + "无预览"提示
  4. 预览图随主题包分发；v4 镜像为内置主题预生成
  - 备选（不推荐）：选中时临时加载主题渲染一帧——实现复杂、可能闪屏、主题缺资源时崩溃
  - 与 N10（ES 源码改造）同批实施


### N4 · U 盘直读

- 通过 OTG 转接头读 U 盘（ROM、存档、备份）
- 系统内挂载/卸载，不靠第三方工具

### N5 · 减少插拔卡

- 用户痛点：**反复插拔卡容易坏；卡 2 读取不稳定、切换失败**
- 方向：**系统层面**解决（比如选中卡 2 后由系统重新挂载/切换），
  而不是让用户装一堆工具

### N7 · 热键提示浮层（2026-11-15 拙木提）

- 按下某种"热键"时，屏幕弹一个列表：`组合键 = 效果`（如 `Select+Start = 退出游戏`、`FN = 菜单`）
- 用户不用背组合键，按一次就能看到全部可用热键
- 后续实现：RA 里可用 OSD，ES 里用主题 overlay；系统级可用 padmerge 检测组合后触发

### N6 · 系统级工具收敛

- "不用导那么多 tool"——能进系统的能力就不要做成外挂脚本
- 但克制：新功能必须评估启动时间和内存开销

## 七、新增需求（2026-11-15，群里许愿）

### N8 · 模拟器 / 核心更新器

- **来源**：群友问“这种系统的模拟器都是死的，用 AI 更新太麻烦，能不能加模拟器更新？比如 PPSSPP、GBA”。
- **结论**：可做，而且换 Debian 13 之后比旧系统容易得多。
- **技术事实**：
  - Debian 13 源里有 `retroarch`、`libretro-mgba`（GBA）等核心，可直接用 apt 更新。
  - Debian 默认关闭 RetroArch 自带的 core updater，因为 apt 管更新；核心在 `/usr/lib/*/libretro/`。
  - PPSSPP 不在 Debian 源里；libretro buildbot 的 aarch64 支持要实测。RK3326 跑 PSP 主要是硬件瓶颈，更新版本不会突然变快。
- **设计**：
  - 菜单加“模拟器 / 核心更新”：检查版本 → 下载 → 校验 → 安装 → 回滚。
  - **只推 TreeOS 验证过的版本**，不无脑跟上游；新核心可能更慢或改存档格式。
  - 自建测试源（.deb 或 core 包），不要依赖构建机/个人目录。
- **优先级**：第一版先保证游戏体验 + 刷完即开机，更新器排后。
- **待确认**：群友最想先更哪个（GBA / PS1 / SNES / PPSSPP），按需求排序。

#### 实现思路（2026-11-15 补充，给实现者）

1. **核心目录不一致要先解决**：我们现在的 RetroArch 是 Debian 版，
   配置里 `libretro_directory` 仍指向 `~/.config/retroarch/cores`（ArkOS 遗留路径），
   而 apt 装的核心在 `/usr/lib/aarch64-linux-gnu/libretro/`。
   两种做法（二选一）：
   - A：把 `libretro_directory` 改成系统目录，es_systems 里的核心名保持 `<core>_libretro.so`
   - B：保持现状，由更新器把 `.so` 原子拷进配置目录（先 `.bak` 再替换）
   **推荐 A**：apt 管版本、可 `apt-get download` 离线包、回滚 = 重装旧版 deb。
2. **更新器形态**：`treeos-cores`（Python，单文件 + systemd 无需常驻）
   - `list`：读本地 manifest，显示已装/可更新
   - `update <core>`：下载 → sha256 校验 → 备份旧 .so → 替换 → 失败自动回滚
   - 自带测试源（放我们服务器），不依赖 GitHub/buildbot
3. **只推验证过的版本**：manifest 里写死版本 + sha256 + 测试记录（哪个 ROM 跑过、
   帧率、存档格式），新核心先在开发机验证再进 manifest。
4. **PPSSPP**：ArkOS 里是独立程序（不是 libretro 核心），Debian 源是否有 aarch64 包
   需在真机 `apt-cache policy ppsspp` 确认；没有就自建包或继续用现成版本。
   RK3326 跑 PSP 是硬件瓶颈，更新版本不会变快，**别把它当卖点**。
5. **入口**：ES 菜单「工具 → 核心更新」，只读展示 + 单个按钮；
   进度用标题栏文字，不要做复杂 UI（1GB 内存 + 小屏）。
6. **验收**：更新后 GBA 进游戏出画面、存档可读；回滚后恢复原状。

## v4 发布前必须做：清除个人数据（2026-11-15，安全）

v3 镜像是从**母卡 rootfs** 直接打包的，因此继承了：

- `/etc/NetworkManager/system-connections/*` —— **家庭 WiFi SSID 和密码**
- `~/.ssh/`、`/root/.ssh/` —— 可能的登录密钥
- shell 历史、日志、截图
- `~/.emulationstation/gamelists` —— 母卡的游戏列表缓存（新卡上会显示不存在的 18 个游戏）

**公开镜像前必须**：
1. 删除所有 NetworkManager 连接配置
2. 删除 SSH 密钥与 authorized_keys
3. 清空 bash/zsh 历史、/var/log
4. 清理 gamelist / 缩略图缓存 / saves / states
5. 构建脚本里加一条"敏感文件扫描"，发现 wifi 配置就中止

自用卡可以保留；**对外发布的 v4 必须干净**。

6. **内置 polkit 网络授权**：`/etc/polkit-1/rules.d/49-treeos-network.rules`，
   允许 `tree` 用户管理 NetworkManager（否则 ES 的 WiFi 菜单连不上新网络）

## 拓展方向评估：机器人遥操作上位机（2026-11-17）

> 来源：另一条工程线（B601/LeKiwi 机械臂遥操作）提出，用 R36S 做「上位机」而非仅手柄。
> 定位为**拓展方向候选**，不进入 v4 主线；主线仍是 Flash 游戏验证。

### 一句话定位

TreeOS 不只是掌机系统，也可以是一台约 ¥150 的机器人遥操作上位机：
USB 串口直连机械臂主控，跑 30–50 Hz 控制环，屏幕显示状态，实体键做硬件急停。

### 最小闭环

```
掌机读摇杆（evdev /dev/input/eventX）
  → 定长数据包（8–16B，序号 + 单调时钟）
  → UDP → 主机 / 机械臂主控
主机回传状态（30 Hz，同一个 socket 反向）
  → 屏幕显示（SDL2 + kmsdrm 或直接 fb0）
  → 实体急停（不走 WiFi、不依赖用户态主进程）
```

### 软件前提（我们需要补的）

1. **内核模块**：`CONFIG_USB_SERIAL_CH341=m`、`CONFIG_USB_SERIAL_PL2303=m`。
   现状：CP210x / FTDI 已编译为模块，CH341/PL2303 未开——主流机械臂主控和主手
   多用 CH340，缺这个直接不通。已登记为 D19。
2. **用户态**：Debian 13 自带 Python 3.13 足够；极限低延迟用 C
   （evdev + 串口 write + UDP socket，几百行，无第三方依赖）。
3. **急停通道**：必须有独立于 WiFi 和用户态主进程的切断方式
   （GPIO 直连主控 EN，或独立串口发 disable）。软件急停只能作为辅助。

### 对方验证过的机器人侧事实（作为输入）

- 机械臂/底盘控制环 30–50 Hz 足够，100 Hz 是加分项；**手感取决于抖动而非平均延迟**；
- 数据包 8–16 字节定长，带序号 + 时间戳；主机侧 200 ms 超时自动停；
- 死区建议 8–12%，**死区内发零速而不是不发包**（不发包会被判超时）；
- 状态回传 30 Hz 够用；
- 屏幕侧 SDL2 + kmsdrm 可用，最省事是 fb0 + evdev，不引入 X。

### 风险

| 风险 | 说明 / 缓解 |
|---|---|
| 2.4G WiFi 抖动 | RTL8188EU 平均延迟尚可但抖动大；控制环 30–50 Hz + 序号/超时；有条件用 USB 网口 |
| USB 供电 | WiFi 峰值 ~300mA，CP210x/CH340 <50mA，USB-CAN 100–200mA；四口改造用带供电 hub，别从掌机取电带执行器 |
| 急停可靠性 | 必须硬件/独立通道，不能只依赖 WiFi 或主进程 |
| 范围蔓延 | 不进入 v4 主线；先由对方在 x86 上跑通最小闭环，再评估是否纳入仓库 |

### 验收标准（对方提出）

- 掌机 50 Hz 发包持续 10 分钟：主机侧丢包率 < 1%，最大间隔 < 100 ms；
- 拔网线 1 秒内主机侧必须停；
- 实体急停在主进程被杀、WiFi 断开时仍然有效。

### 协作状态

- 对方先在 x86 主机用现成手柄跑通「evdev → UDP → 机械臂」，代码按能直接跑在 A35 上写
  （纯 C 或纯 Python 标准库，无第三方依赖）；
- 跑通后把代码和实测数据给我们，再决定纳入仓库或仅作为文档示例；
- 我们这边待补：CH341/PL2303 模块（D19）、50 Hz 抖动实测（设备网络稳定后）。

### 外部意见附注（GPT-6-Astra，2026-11-17）

1. **最大盲点：把实体键当「硬件急停」不成立。** 按键仍要经过 Linux 输入、用户态进程、串口三层，
   系统卡死时可能失效。安全闭环应放在**主控侧**：指令超时自主停机 + 一条不经过 CPU 的
   独立断使能通路（GPIO 直连 EN 或动力回路）。30–50 Hz 的平均频率不是关键，
   **最坏延迟和失联行为**才是。
2. **方向不冲突，投入会冲突。** 保持独立验证；串口驱动、供电和安全改造不得挤占
   v4 Flash 验证的时间。
3. **只做一件事验证生死**：低能量、限位条件下的 USB 串口故障注入闭环测试——
   50 Hz 发指令同时刷新屏幕，主动卡死进程、拔线，检查主控能否在预定安全时限内可靠停机。
   **过不了就暂停该方向。**

> 采纳：原「实体键急停」改为「软件急停（辅助）+ 主控超时自停 + 独立断使能通路（必须）」；
> 第 3 条作为该方向的准入门槛写入验收标准，不通过不启动后续开发。

## 多 SoC 与 ports 兼容（2026-11-18，外部评审 gpt-6.luna）

> 完整评审：`08_外部评审-OldBits与多SoC-gpt6luna.md`

**多 SoC 结论**：不做「一个镜像盲猜所有板子」，做「**共用 arm64 rootfs + 每 SoC 内核/模块包 + 每设备启动包**」。
设备包包含 bootloader、DTB、面板、WiFi、电源、输入；用户态（ES/RA/Ruffle/ports 启动器）尽量一份。
统一输入契约：每块板最终只暴露**一个**标准手柄（RK3326 保留内核 `odroidgo3-joypad`；
H700/RK3566 用板级驱动或轻量 uinput 桥，设备名固定 `TreeOS Gamepad`）。

**ports 结论**：先做「manifest + 统一 port-runner + 隔离目录」契约，不接下载商店；
兼容等级 L0 能装 / L1 能启动 / L2 可玩 / L3 推荐。未实测前最多标 L1。
性能门槛（L2）：目标 30 FPS，P95 帧时间 ≤40ms、P99 ≤67ms，RSS ≤450–500MB，余量 ≥150MB；
连续 20 分钟热降频不得让帧率较基线跌超 20%。

**承诺边界**：可以承诺原生 ARM64、SDL2/GLES、轻量 2D/独立游戏；
**不承诺** Xbox/PS2 重型 3D、x86 转译、Wine/DXVK 类，也不能因为 RK3566 宣传视频就给 RK3326/H700 承诺。

**优先级**：Flash 仍是主线；ports 试点前两周总工程量 ≤20%，第三周按授权可核验 + 至少一台达 L2 决定是否扩展。

**合规**：不预装、不镜像、不代转存含商业资源的 port；网盘直链聚合也不做。

## 开发平台能力规划（2026-11-18，GPT-6.1 Sol 评审）

> 完整评审：`08_外部评审-开发平台规划-gpt6sol.md`

**定位**：先把 TreeOS 做成「能在掌机上完成一次真实开发任务」的系统，再展示离线 AI。
对外一句话：**「可从游戏前端进入完整开发终端，用标准外设、网络和可复现工具链修改、测试并部署掌机应用。」**

**优先级（收益/风险/工作量）**
1. 可切换的开发终端 + 中文输入 + USB 键盘（基础设施）
2. 云端 coding agent 完成真实仓库任务（云端推理；优先试 Codex CLI 的 arm64 静态包，不必常驻 Node）
3. 串口/GPIO + 受控遥操作实验台（安全链在机器人侧，实体急停独立于掌机/WiFi/进程）
4. Flash 轻量滤镜（色彩/扫描线/锐化；合成层额外内存 ≤40MB，相对无滤镜帧率下降 ≤10%）
5. 0.5B 本地模型（技术展示；1B 在 1GB 上不建议作为产品能力）

**资源预算（设计门槛，非实测）**
- 开发档：终端+IME+agent 峰值 PSS ≤300–400MB，连续 60 分钟 ≥10 次编辑/测试循环无 OOM；
- 遥操作：30–50Hz，接收端 150ms 无新命令进入安全态，故障注入（断网/崩溃/卡键）必须通过；
- 模型：Qwen2.5-0.5B GGUF Q4_K_M（约 429MB 权重），推理进程 ≤700MB，首 token ≤10s、持续 ≥2 tokens/s 才考虑对外；
- 互斥档位：游戏档 / 开发档 / 推理档，一次只给一个前台程序 DRM master；先测再定 MemoryHigh/Max。

**公开策略**：建 `treeos-labs` demo 仓库，放三项旗舰 demo 的源码、设备配置、构建与测试脚本、逐设备结果；主仓库只收成熟功能。
**避免噱头**：发布完整任务、计时、峰值内存、失败案例、构建命令和原始日志；遥操作视频必须展示断链和急停。

## 设备矩阵与上游复用（2026-11-18，修正）

> 之前文档写得太偏 RK3326，这里明确：**TreeOS 不是单机型系统**。

| SoC / 设备 | 现状 | 上游支持 |
|---|---|---|
| RK3326（R36S） | 已验证：6.12 + 合并手柄 + Flash | ROCKNIX 有完整补丁栈（002 gpiolib legacy、003 input-polldev、004 input-drivers、面板/DSI PHY/电源） |
| RK3566（RGB30/RG353 等） | 已采购，物流中；到货前不写“已支持” | 上游 mainline 有大量机型 DTS；ROCKNIX 有面板、ADC keys、电池、WiFi、joypad 补丁 |
| Allwinner H700（RG35XX 系列） | 未开始 | ROCKNIX 有面板、joypad、OTG host、电池、RTC 补丁 |
| RK3562（用户新购） | 已采购，物流中；到货前不写“已支持” | **上游只有 SoC dtsi + EVB**，没有掌机 DTS；ROCKNIX 无该设备包。需要 bring-up（厂商 BSP 或自己写板级 DTS），周期最长 |

### 结论：内核层改成「复用 ROCKNIX 补丁栈」，不再自己重写

调查 ROCKNIX `distribution` 仓库（GPL）后确认：
- 我们手写的 6.12 兼容移植（`input-polldev`、`of_gpio_legacy`）在 ROCKNIX 里就是
  `003-input-add-input-polldev-driver.patch` 和 `002-gpiolib-of-legacy-api.patch`——
  他们选择**把老 API 加回来**，驱动本体一行不改；比我们逐处改驱动更省维护。
- RK3326/RK3566/H700 的面板、DSI PHY、按键、电池、WiFi、OTG 补丁都已存在。

**修正后的分层**：

| 层 | 来源 |
|---|---|
| 内核 + 设备树 + 面板 + 输入 | **ROCKNIX 补丁栈**（按设备目录），pin 一个内核版本（6.12 LTS 或 6.18 LTS） |
| 用户态 rootfs | TreeOS（Debian 13），可参考 dArkOS 的打包与 ES 配置 |
| 前端 / Flash / 开发平台 / 多设备安装器 | TreeOS 差异化部分 |

> dArkOS 的上游是 Debian Trixie 用户态，但 R36S 社区版内核仍是 4.4/5.10，不是 6.12；
> 它适合参考 rootfs/ES/打包，不适合作为内核来源。

**下一步**：
1. 把我们的补丁与 ROCKNIX RK3326 补丁逐条 diff，重复项退役；
2. 用 ROCKNIX 补丁栈 + 6.12/6.18 重建内核，先在 R36S 验证；
3. 设备目录按 ROCKNIX 结构建 `devices/<soc>/<board>/`，RK3566 其次，RK3562 单独立项评估。

### Flash 运行时修订（2026-11-18，补充评审）

> 完整版：`08_外部评审-Flash运行时修订-gpt6sol.md`

**主线选择（已更正）**：新运行时（Weston + wgpu，42MB，fontconfig 中文正常）作为 **2GB 能力档的目标运行时**；
**1GB 是基线，冻结核心继续作为 1GB 的默认与回滚路径**。2GB 不是 TreeOS 的前提、不是默认、不是排期项；
不改机的用户照样受支持，不能因为没有 2GB 就把用户排除在外。
**现在不能切默认**：完整手柄试玩、FN、退出、存档、30 分钟压测都没验收。

**切默认门槛（2GB）**：
- 中文 3 款无方框；输入 3 款各试玩 20 分钟无丢键/双指针；
- FN 开合 10 次、Select+Start 退出 10 次都回 ES 无残留；
- 存档「保存→退出→重启→读取」3 次一致，且不在 tmpfs；
- 30 分钟无崩溃，`MemAvailable ≥256MB`、10 分钟平均换入 <5MB/分钟；
- 启动 P95 ≤10 秒，且比冻结核心同游戏增加 ≤3 秒。
出现存档丢失、无法退出、普遍输入回归、OOM/卡死、中文回退 → 立即回滚冻结核心。

**Weston**：先按游戏会话启动、退出关闭；只有常驻能把 P95 降低 ≥2 秒且 2GB 空闲 `MemAvailable ≥512MB` 才考虑常驻。1GB 不建议常驻。
**profile**：单一 schema（带版本号）同时生成旧 `config.ron/.stick` 与新 `-B`/padmouse 配置；生成物不手改；未知字段报错不静默丢弃。
**对外承诺（按设备能力分档，不做全局门槛）**：
- **1GB 基线**：冻结核心 + 逐款验证的 Flash 2.6；3.2 不列标准能力（2G swap 能启动但卡顿，不作可玩承诺）；
- **2GB 可选档（不排期）**：仅在用户自行改装时可用；新运行时 + 3.2 逐款验证，完成输入/存档/30 分钟后才进清单；不代表全部 3.2 可玩；
- 文档只记录分层与事实，**不得把「改 2GB」写成使用 TreeOS 的前提**。
**暂不重开**：LD_PRELOAD 呈现拦截、旧核心字体注入、安卓 AIR 解包、扩大 zram。

**归档**：可发布的 `treeos-flash2`、profile schema/适配器、设备启动包、验收脚本进主仓库；
未通过的 KMS 直出原型与失败实验进 labs；失败项（LD_PRELOAD、字体注入、AIR 3.7.3、三轮 zram、旧 cross 依赖）写进 `docs/decisions/`。

### Panfrost GPU hang 定位（限 2 人日）

- 固定 6.15.6/供电/SWF 哈希/存档/分辨率/入关动作，每组 5 次、每次 5 分钟；记录超时次数、首次时刻、Mesa/Ruffle 版本、温度、MemAvailable、swap；另跑稳定 3D/Flash 负对照。

### 1GB 上「增强模式」的晋级门槛（按游戏，不按容量一刀切）

候选各跑 3 次冷启动 + 20 分钟实玩，覆盖最重关卡：

- 3/3 完成；GPU timeout / OOM / 崩溃 / 卡死 0；中文、映射、退出正常，需指针者无双光标；
- P95 帧时间 ≤1.5× 原生帧预算；每 10 分钟 >250ms 停顿 ≤1 次（不要按 60Hz 错杀 24/30fps）；
- 最重场景 MemAvailable 不连续 10 秒 <64MiB；不持续 10 秒换入且伴随 >250ms 停顿；已用 swap 不单独判失败；
