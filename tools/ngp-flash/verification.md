# 两台掌机实测：保留 RK3326 原入口，区分三个问题

## 1. 旧版是什么，新的渲染路径能否在旧设备工作？

在 RK3326 实机上只读核对：aarch64 Linux 6.15.6，系统报告约 955 MiB 内存，面板模式 640×480。ES 的 Flash 项读取 `/roms/flash` 的 SWF，经 `flash-es-launch` 和 `treeos-flash` 选择后端；classic 走 RuffleHandheld，增强版走 Weston + `ruffle_desktop`（报告 `0.7.1-local`, `bd401e66…`）。这不是 NGP 的 `release-ui8` / KMS worker。没有替换旧版或修改 ES 配置。

用原创四色角标 SWF（舞台 600×400）在 RK3326 的 **Mesa / Mali-G31 (Panfrost)** 离屏表面分别运行已装 classic `native_v020` 和 NGP 已验证的共用二进制 `dc9e2434…`。在 SDL swap 前读回 640×480 像素：新播放器的四角、中央和上下黑边全部通过；旧 classic 的四角和中央也在，但上下边缘为灰色背景，不符合此例的黑边预期。这个结果只验证播放器和最终合成；不是 RK3326 的实屏、M 菜单、退出或噩梦战斗验收。不能将 NGP 的背光和 systemd worker 直接装上去。

## 2. 共用时间线补丁有无潜力？

相同 aarch64 无窗口 QA 程序、相同原创嵌套 MovieClip 负载，单核、默认调频、A/B/B/A，每次预热 45 帧再取 180 帧。A 是参照，B 只增加 `qa/ruffle-timeline-empty-queue.patch`。表中为每个版本两轮 P95 的平均，单位 ms/次时间线更新，越小越好。**不是两机已装启动器的 FPS，也不包括显示和 GPU。**

| 设备 | 稳定对象 A → B | 频繁增删 A → B |
|---|---:|---:|
| RK3326 | 41.25 → 38.49 | 60.56 → 55.79 |
| RK3562 | 15.11 → 14.34 | 24.11 → 23.82 |

## 3. NGP 真实游戏能否证明应该升级？

Road 666，隔离存档副本，同一输入序列，1024×768 的 Mali-G52 EGL 离屏、高画质不跳帧。窗口前后分别截图确认战场，仅按单调时钟窗口内的完整 swap 区间计数。以下为带同一测量工具的诊断构建，不是与已装正式二进制的直接比较。主对照 A1 → B1 → A2，稍后又单独复测候选 B2；两组间做过独立小负载测试，非锁温、非锁步敌群。

| 战场窗口 | 呈现帧/秒 | 呈现间隔 P95（ms） |
|---|---:|---:|
| A1 参照 | 7.45 | 218.0 |
| B1 候选 | 12.66 | 131.3 |
| A2 参照 | 7.36 | 332.1 |
| B2 候选复测 | 4.48 | 462.8 |

**决定：不升级默认播放器，也不凭 B1 的好成绩按游戏启用。** 四次最慢 5% 单帧 tick 的线程 CPU 时间仅占墙钟的约 23–35%，说明不少时间线程未在执行，不能直接认定为 GPU 等待。下一轮应该同步记录调度、缺页/换页、温度与频率及敌群状态，再区分计算优化与等待波动。在有显著可重复收益前继续保留现有回退路径。
